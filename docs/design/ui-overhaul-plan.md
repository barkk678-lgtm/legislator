# תכנית עבודה: מעבר לעיצוב לפי המוקאפ

מסמך תכנון בלבד - שום קוד לא שונה בעקבותיו. נכתב לקראת המשך העבודה,
לפי docs/design/legislator-mockup.html ו-docs/design/README.md
(המפרט העיצובי שכבר קיים). לא נוגע במנוע/ולידטור/רנדרר - כל התכנית
כאן היא apps/api/templates, apps/api/static בלבד.

## המצב הנוכחי (לפני התכנית)

- `index.html`/`app.js`/`style.css` מיישמים היום מסך אחד: עריכת הצעת
  חוק (edits+insertions -> render -> docx), בלי תפריט צד, בלי
  לשוניות. זו בדיוק הלשונית "הצעות חוק" במוקאפ - שום דבר אחר.
- שש הלשוניות הנוספות במוקאפ (נוסח משולב, שאילתות, הצעות לסדר, מומחה
  התקנון, סיכומי פרוטוקולים, מחקר) הן **תכנון עתידי בלבד**: אין להן
  שום backend, שום endpoint, שום לוגיקה קיימת. המוקאפ מציג אותן מלאות
  (עם תוכן מדומה), אבל זה מפרט עיצובי - לא אישור לבנות אותן עכשיו.
- הלוגיקה האינטראקטיבית שנבנתה במשימה 10ב (רינדור-מחדש מלא של העץ,
  דקורציית del/ins, תפריט הוספה היררכי עם תצוגה מקדימה של מספור,
  עריכת כותרת שוליים, מונע-מרוץ מול הקלדה פעילה) **נשארת כפי שהיא
  לגמרי** - זה בדיוק מה ש-README אומר לא לקחת מהמוקאפ ("מנגנוני
  האינטראקציה - קיימים בקוד ונשארים כפי שהם").

## שאלה פתוחה שצריך להכריע לפני שמתחילים (לא ניחוש)

**מה עושים עם שש הלשוניות שאין להן backend?** שלוש אפשרויות:
1. לא בונים אותן בכלל כרגע - רק "הצעות חוק" קיימת בתפריט הצד.
2. בונים את התפריט עם כל שבע הלשוניות מוצג, אבל שש מהן מנוטרלות
   (disabled, עם תווית "בקרוב") - כדי שהמסגרת הכללית תיראה כמו המוקאפ
   מהיום הראשון, גם אם רק אחת פעילה.
3. בונים את השבע כמו במוקאפ, כולל תוכן מדומה סטטי (בדיוק כמו במוקאפ) -
   כדי לקבל תחושה מלאה של המוצר, אבל בלי לחבר שום דבר ל-backend אמיתי.

**המלצה: אפשרות 2.** נותנת את המסגרת הנכונה (תפריט צד, בררת לשונית)
בלי לבזבז זמן על תוכן מדומה שיושלך, ובלי ליצור רושם שגוי שפיצ'רים
עובדים כשהם לא. אבל זו החלטת מוצר, לא טכנית - צריך אישור לפני שמתחילים.

## שלבים

### שלב 0 - הכנה
- להריץ `pip install pyluach` (נוסף ל-requirements.txt) בסביבת הפיתוח,
  אם עוד לא הותקן.
- לוודא ששרת ה-uvicorn עולה נקי לפני שמתחילים לגעת ב-HTML/CSS.

### שלב 1 - מסגרת (Shell): תפריט צד + topbar לפי לשונית
קבצים: `index.html` (מבנה חדש), `style.css` (משתני CSS + `.rail`/`.nav`/
`.topbar` מהמוקאפ), `app.js` (מיתוג לשוניות בלבד - עדיין בלי שינוי
ללוגיקת "הצעות חוק").

- להעתיק את משתני ה-CSS מהמוקאפ (`:root { --navy, --flag, --tint, ... }`)
  לתוך `style.css`, ולמפות את הצבעים הקיימים (`--accent`, `--accent-bg`
  וכו') אליהם - לא למחוק את מה שהוולידטור/status-badge כבר תלויים בו,
  רק להחליף את הפלטה שמאחוריהם.
- להוסיף גופנים: Frank Ruhl Libre (לנוסח החוק ולטבלת ההצעה) + Assistant
  (לכל השאר) - `<link>` ל-Google Fonts כמו במוקאפ.
- לבנות את מבנה `<nav class="rail">` עם שבע הלשוניות (או אחת, לפי
  ההחלטה למעלה) ו-`<div class="main">` עם `.topbar` נפרד לכל לשונית -
  בדיוק מבנה המוקאפ (`data-bar="bills"` וכו').
- JS: מתג לשוניות פשוט (`.nav button` -> `.tab.on` + `[data-bar]` -
  בדיוק הקוד הקטן שכבר קיים בתחתית המוקאפ עצמו, אין צורך להמציא מחדש).
- **קריטריון סיום:** האתר עולה, מציג את תפריט הצד והלשונית "הצעות
  חוק" פעילה, בלי שום שינוי בהתנהגות בפועל (אותה עריכה, אותם endpoints).

### שלב 2 - "הצעות חוק": מבנה החלוניות + טופס פרטי ההצעה
- להעביר את הטופס (שם הצעה, שם יוזם, דברי הסבר) למבנה `.meta`/`.fld`
  של המוקאפ - שים לב: המוקאפ מציג גם שדות "תאריך הנחה" ו"מראה מקום",
  אבל אלה **הוסרו בכוונה** מהמערכת (10ב, החלטה מאושרת) - לא להחזיר
  אותם. שני השדות שנשארים: שם ההצעה (עכשיו עם ברירת מחדל אוטומטית,
  ראו bill_title.py) ושם היוזם. מראה המקום מוצג כטקסט read-only
  (`#source-ref-note` הקיים), לא כשדה קלט.
- `.cols`/`.card`/`.card > header` - לעטוף את שתי החלוניות הקיימות
  (עץ העריכה מימין, תצוגת הוורד משמאל) במבנה הכרטיסים של המוקאפ,
  כולל הכותרת הכפולה (h2 + span תיאור קצר).

### שלב 3 - עץ העריכה (`.law`, `.sec`, `.addbtn`)
זה החלק הכי רגיש - כאן כל הלוגיקה האינטראקטיבית מ-10ב חייבת להמשיך
לעבוד בדיוק כפי שהיא, רק על מבנה DOM/קלאסים חדש.

- מיפוי קלאסים: `.node` (הקיים) -> משמר את מבנהו הפנימי (`.node-header`,
  `.node-body-row`, `.node-text`, `.node-margin-title`), אבל מקבל את
  העיצוב הוויזואלי של `.sec`/`.sec-title`/`.sec-body` מהמוקאפ (רשת
  128px+1fr, גופן Frank Ruhl Libre, `<i>` לתיוג "סעיף N" קטן ואפור).
- כפתור ה-"+": המוקאפ ממקם אותו כ-`.addbtn` עם `position:absolute`
  משמאל לכל `.sec` (מופיע ב-hover על כל הסעיף). זה **שונה** מהמיקום
  שנקבע במשימה 10ב (בסוף שורת הטקסט, לפי משוב מפורש של המשתמש: "אני
  רוצה שהפלוס... יהיה בסוף שורה... איפה שנגמר הטקסט"). **סתירה של
  ממש בין שני מקורות - לא להכריע לבד, לשאול את המשתמש** באיזה מהשניים
  לבחור (או לשלב: מיקום המוקאפ אבל רק ב-hover על השורה הספציפית, לא
  על כל הסעיף).
- דקורציית del/ins: כבר קיימת ועובדת - רק לעדכן צבעים/גופן ל-`--del`/
  `--ins` של המוקאפ (במקום `--danger`/`--accent` הנוכחיים).
- תוכן שהוכנס (`.inserted`, רקע צהוב): המוקאפ לא מדגים את המקרה הזה
  במפורש, אבל `--touched-bg`/`.fresh` (המשמש בטבלת ההצעה) הוא בדיוק
  אותו רעיון - להשתמש באותו צבע רקע צהוב גם בעץ העריכה.

### שלב 4 - תפריט ההוספה ההיררכי (`.pop`)
המוקאפ מדגים בדיוק את מה שכבר בנוי (משימה 10ב): רשימת אפשרויות עם
תצוגה מקדימה של המספור ("סעיף קטן יהיה (א1)"), פריט מנוטרל להסבר
("פסקת משנה תיפתח אחרי שתתווסף פסקה"). בעיקר עדכון ויזואלי (`.pop`/
`.pop button`/`.pop button u`), לא לוגי - `toggleInsertMenu`/
`showInsertForm` הקיימים ממשיכים לעבוד, רק הקלאסים/מיקום ה-popup
(`position:absolute` יחסית ל-`.sec`, לא `.insert-host` נפרד) משתנים.

### שלב 5 - גיליון הוורד (`.sheetwrap`/`.sheet`/`.tbl`)
עיצוב "דף נייר" - `renderDocxApprox` הקיים ממשיך לבנות את אותן שורות
מ-`data.lines`, רק העיצוב (`.tbl .mg`/`.tbl .no`/`.fresh` לסימון שורה
שהשתנתה) מוחלף לפי המוקאפ. `.fresh` (רקע צהוב + פס צהוב בצד) הוא
המקבילה הוויזואלית ל"סעיף נגוע" (touched) - יש כבר `touched_sections`
בתשובת ה-API לשימוש הזה.

### שלב 6 - ניקוי
- להסיר קלאסים/כללי CSS ישנים שכבר לא בשימוש אחרי המעבר.
- להריץ שוב את `tests/e2e_10b_playwright.py` (מעודכן לפי מבנה ה-DOM
  החדש איפה שנדרש - בעיקר סלקטורים כמו `.node-header`, `.node-add-btn`
  שעשויים לזוז מקום) - **קריטריון קבלה: אותם 21 הבדיקות שעברו היום
  ממשיכות לעבור**, לפני שמדווחים שהמעבר הושלם.

## מה *לא* בתכנית הזו (ולמה)

- שש הלשוניות האחרות (שאילתות, הצעות לסדר וכו') - אין להן backend,
  ראו "שאלה פתוחה" למעלה. אם ההחלטה תהיה אפשרות 3 (תוכן מדומה מלא),
  זו תכנית נפרדת.
- שום שינוי ב-packages/amend, packages/render, packages/validate -
  זו תכנית עיצוב/frontend בלבד.

## סיכום סדר עבודה מוצע ליום העבודה

1. להכריע בשאלה הפתוחה (היקף שבע הלשוניות) + בסתירת מיקום כפתור ה-"+".
2. שלבים 1-2 (מסגרת + טופס) - שינוי נמוך-סיכון, אפשר לבדוק ויזואלית מהר.
3. שלב 3 (עץ העריכה) - הכי רגיש, לבדוק אחרי כל תת-שינוי שהעריכה/
   הדקורציה/ה-caret עדיין עובדים (בדיוק כמו שנבדק היום).
4. שלבים 4-5 (תפריט הוספה + גיליון) - בעיקר CSS.
5. שלב 6 (Playwright + ניקוי) - לפני שמדווחים "סיימתי".
