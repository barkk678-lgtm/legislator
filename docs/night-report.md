   - **בקשות אישור לכל חוק בנפרד** (Supabase MCP `execute_sql`)

   - **תקלת תשתית באמצע העבודה** - restart של הקונטיינר מחק את כל

     SQL מהזיכרון במקום להעתיק verbatim, והחדיר `parent_id` שגוי.
     ה-DB נוקה לחלוטין (`laws`/`law_versions`) והטעינה התחילה מחדש
     מאפס, עם כלל חדש ומחייב: **תוכן SQL שמבוצע חייב להיות שעתוק
     מדויק, אף פעם לא הקלדה-מחדש מהזיכרון.**

   **הפתרון הסופי:** גילוי שסביבת ה-agent הזו לא מחזיקה חיבור TCP
   ישיר ל-Postgres בכלל (רק פורט 443/HTTPS פתוח - נבדק ישירות,
   `psql`/`psycopg` לא רלוונטיים כאן, גם לא ל-pooler). נבנה
   `tools/load_corpus_to_supabase_rest.py` (+ `packages/corpus/
   sql_parser.py`) שמפרסר מכנית (בלי LLM) את קובצי ה-SQL שכבר
   אומתו, ושולח אותם כ-JSON ישר ל-REST API של Supabase (`service_role`
   key, שהתקבל מברק ולא נשמר בשום קובץ) - אפס תוכן קורפוס עובר דרך
   קונטקסט ה-LLM, ואפס בקשות אישור בפועל. הפרסר עצמו אומת בבדיקת
   round-trip (parse → rerender → diff) על **כל 998 הקבצים, 0
   אי-התאמות**, לפני שהיה מותר להשתמש בו לטעינה אמיתית. שני כשלים
   אמיתיים נמצאו ותוקנו תוך כדי (ראו §3 להלן): באג סכימה
   (`section_amendment_tokens.hebrew_year`) וחוק אחד ענק (4,794
   nodes) שגרם ל-statement timeout - נפתר בפיצול ל-batches.
   commits: `e2a82b9` (תיקון סכימה), `ab80325` (כלי הטעינה).

## 2 · מה נחסם ועל איזו שאלה בדיוק

**עדכון:** הקורפוס המלא **כן** נטען ל-Supabase בהצלחה הלילה (ראו §1
פריט 4) - מה שנשאר חסום כאן הוא רק חיבור `apps/api` (השרת של
האפליקציה, ל-Vercel) לקורפוס הזה, לא זמינות הנתונים עצמם.

**חיבור `apps/api` לקורפוס המלא ב-Supabase (לא רק לשני ה-fixtures)
דורש `psycopg` + `DATABASE_URL` אמיתי - תלות חדשה שלא הותקנה
הלילה, לפי ההוראה המפורשת ("אל תוסיף תלויות; אם צריך pip install -
תתעד ותעבור הלאה").** זה בדיוק המקרה - מתועד כאן ובקוד
(`law_registry.search_law_titles` docstring). **השאלה לברק:** האם
להתקין `psycopg`/`asyncpg` ו-`DATABASE_URL` בסביבת production
(Vercel) כדי לחבר את `apps/api` לקורפוס האמיתי - זו החלטת תשתית
אמיתית (secret management, לא רק pip install טכני), לא הכרעתי
לבד. הלוגיקה עצמה (`law_search.py`) כבר מוכנה ונבדקת במלואה -
כשיהיה חיבור DB, זה drop-in replacement של מקור הרשומות בלבד.

**RLS על 5 הטבלאות מופעל בלי policies (בכוונה, מ-2026-09-13) -
המשמעות: אפילו אם `apps/api` היה מתחבר עם מפתח anon/publishable,
היה מקבל 0 שורות.** גישה אמיתית דורשת או policy מפורש (migration
חדשה - אסור הלילה: "אל תרוץ שום מיגרציה חדשה מעבר למה שנדרש
לטעינה") או חיבור service_role/Postgres ישיר (התלות החדשה שלעיל).
לא הכרעתי לבד - שתי האפשרויות דורשות שיקול אבטחה.

## 3 · ממצאים שדורשים הכרעה שלי

1. **`ח:קטע5`/`ח:קטע4` (משימה D, חוק להגברת האכיפה)** - השימוש
   בפועל בוויקיטקסט סותר את ההחלטה הקיימת בקוד ("קטע4 עוטף רק
   הערה, לא רמת מבנה אמיתית - מדולג לגמרי"). מצאתי מופע אמיתי עם
   כותרת-מבנה מלאה (`{{ח:קטע4|תוספת 2 חלק ב סימן ב|סימן ב׳: בטיחות
   בעבודה|...}}`) - כלומר ייתכן שתוכן-מבנה אמיתי הולך לאיבוד בשקט
   בחוקים שכן נטענים בהצלחה היום, לא רק בחוק שנכשל. **לא נגעתי ב-
   wikitext_parser.py הלילה (כמבוקש) - צריך לחזור ולבדוק את כל
   מופעי `ח:קטע4` בקורפוס לפני החלטה.**

2. **`ח:חיצוני` בחוק הפטנטים (משימה D)** - לא תבנית לא-מוכרת אלא
   המשכיות-משפט-חוצה-שורה שמתחילה בתבנית inline לא-פותחת-שורה.
   אותה משפחת בעיה בדיוק כמו תיקון ה-continuation-attach שכבר בוצע
   הלילה (`packages/corpus/wikitext_parser.py`) - אבל בכיוון הפוך
   (שורה שמתחילה בתבנית מוכרת, לא בטקסט גולמי) שהתיקון הקיים לא
   מכסה. דורש הכרעה תכנונית לפני הרחבת המנגנון.

3. **באג סכימה שתוקן תוך כדי טעינה - `section_amendment_tokens.
   hebrew_year` הוגדר `not null`, אבל המיגרציה שהוסיפה `is_unparsed`
   (`20260914010000`, מה-14.9) מתעדת במפורש שטוקן לא-ניתן-לפענוח
   ("תשס״ה־3 תשע״ד" - הדוגמה המדויקת שהמיגרציה עצמה נותנת, מחוק
   העמותות) אמור להשאיר `hebrew_year` NULL.** סתירה בין הכוונה
   המתועדת לאילוץ בפועל - המיגרציה ההיא הוסיפה את העמודות החדשות
   אבל שכחה להסיר את ה-`not null` המקורי. תוקן במיגרציה ממוקדת
   (`20260915120000`, commit `e2a82b9`) לפי הכלל "מה שהטעינה עצמה
   דורשת" - נבדק שרק חוק אחד (law-2000485) נפגע בפועל לפני התיקון.
   **שווה שברק יבדוק שהתיקון הזה תואם את הכוונה המקורית** - לא
   הכרעה תכנונית חדשה, רק תיקון סתירה פנימית, אבל זו בכל זאת
   מיגרציה שלא תוכננה מראש.

4. **7 חוקים שאיבדו סיווג תוקף מפורש ("תקף" -> "לא ידוע")** בעקבות
   תיקון השנה (ראו §7 ב-TASKS.md לרשימה). לא השפיע על `should_ingest`
   (עדיין נטענים), אבל אם יש בעתיד שימוש שכן תלוי בסיווג תוקף מפורש
   (למשל תג "תקף"/"בטל" מוצג למשתמש) - יוצג "לא ידוע" לחוקים האלה
   במקום "תקף" שהיה קודם (גם אם שגוי-מקור). פשרה מכוונת שבחרתי
   (בטיחות על פני ודאות כוזבת) - אבל שווה שברק יידע שזה קרה.

5. **חיבור DB אמיתי ל-`apps/api`** - ראו §2 למעלה, לא רק "נחסם"
